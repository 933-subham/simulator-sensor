# sensor-sim-api

**Controlled IoT sensor simulator** for smart campus / facility dashboards.  
Serves realistic power-meter and water-tank readings with **manual-only fault injection** — no anomalies unless you create them.

Built for: controlled AI anomaly-model testing · SNS alert verification · live dashboard demos

---

## Quick Start

```bash
git clone <repo-url>
cd sensor-sim-api
npm install

# Copy env template and edit as needed
cp .env.example .env

npm run dev        # development (nodemon auto-reload)
# or
npm start          # production
```

Open `http://localhost:3000/control` — the control panel loads immediately with 24 h of backfilled history.

## Device Model

The simulator is **building-hierarchy-agnostic**. Each device is just:

| Field | Description |
|---|---|
| `deviceId` | Unique ID (generated by simulator) |
| `kind` | `power_meter` \| `water_tank` |
| `label` | Free-text label for the control panel (e.g. "Building A - Floor 2") |
| `claimCode` | One-time token — give to your main website to obtain the device secret |
| `secret` | HMAC signing key — shown only via `POST /api/claim` |
| `status` | `online` \| `offline` \| `fault` |

**Your main website** owns the building/floor/organisation hierarchy and associates devices using `deviceId` after the claim step.

### Claim Flow (main website integration)

```
1. Admin creates device:
   POST /api/devices  → { deviceId, claimCode }   (no secret yet)

2. Admin shares claimCode with the main website out-of-band.

3. Main website claims device (one time only):
   POST /api/claim  { claimCode }  → { deviceId, kind, label, secret }

4. Main website stores secret and uses it to:
   a) Verify inbound push signatures from the simulator
   b) Optionally push readings back via POST /api/push/:deviceId
```

### Push Endpoint

External devices (or your test scripts) can push readings signed with the device's HMAC secret.

**Signature format:**
```
HMAC-SHA256(secret, deviceId + "." + timestamp + "." + seq + "." + canonicalJson(values))
```

Where `canonicalJson` = `JSON.stringify` with keys sorted **alphabetically**.

**Node.js verification example (for your main website):**
```js
const crypto = require('crypto');

function verifyReading(secret, req) {
  const { deviceId, timestamp, seq } = {
    deviceId:  req.headers['x-device-id'],
    timestamp: req.headers['x-timestamp'],
    seq:       req.headers['x-seq'],
  };
  const incomingSig = req.headers['x-signature'];

  // Canonical JSON — sort keys alphabetically
  const values = req.body.values;
  const canonical = JSON.stringify(
    Object.fromEntries(Object.entries(values).sort(([a], [b]) => a.localeCompare(b)))
  );

  const payload  = `${deviceId}.${timestamp}.${seq}.${canonical}`;
  const expected = crypto.createHmac('sha256', secret).update(payload).digest('hex');

  const a = Buffer.from(incomingSig, 'hex');
  const b = Buffer.from(expected,    'hex');
  if (a.length !== b.length) return false;
  return crypto.timingSafeEqual(a, b);
}
```

**Push a reading:**
```bash
# Compute signature first
SECRET="sk_..."
DEVICE_ID="dev-abc123"
TS=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
SEQ=101
VALUES='{"current":60.1,"energy_kwh":1205.3,"frequency":50.01,"power_factor":0.930,"power_kw":42.3,"voltage":229.8}'
PAYLOAD="${DEVICE_ID}.${TS}.${SEQ}.${VALUES}"
SIG=$(echo -n "$PAYLOAD" | openssl dgst -sha256 -hmac "$SECRET" | awk '{print $2}')

curl -X POST "http://localhost:3000/api/push/${DEVICE_ID}" \
  -H "Content-Type: application/json" \
  -H "x-device-id: $DEVICE_ID" \
  -H "x-timestamp: $TS" \
  -H "x-seq: $SEQ" \
  -H "x-signature: $SIG" \
  -d "{\"values\":${VALUES}}"
```

### Secure Cloudinary Storage & Media Delivery

Enterprise cloud storage integration for telemetry proof documents, fault incident images, and maintenance audit photos.

#### Key Security Principles
1. **Secrets Isolation**: Cloudinary `API_SECRET` is held strictly in `.env` and **never** transmitted to the browser or frontend clients.
2. **Strict Redaction**: `GET /api/storage/status` displays masked API keys and returns zero secret material.
3. **HTTPS Enforced**: All asset delivery URLs force `secure: true` (`https://`).
4. **Direct Client Upload Signing**: `POST /api/storage/sign` generates cryptographic HMAC-SHA signatures on the backend so clients can upload directly without leaking secrets.
5. **Payload Sandboxing & Validation**: File types are whitelisted (JPEG, PNG, WebP, SVG, PDF, CSV, JSON), maximum file size is enforced (10 MB), and `public_id` paths are sanitized against directory traversal.

#### Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/storage/status` | Check storage connection, quotas, and limits (masked credentials) |
| `POST` | `/api/storage/upload` | Upload file via multipart form-data (`file`), remote `url`, or base64 |
| `POST` | `/api/storage/sign` | Generate signed parameters for secure direct-to-cloud client uploads |
| `GET` | `/api/storage/url/*` | Generate optimized delivery URLs with auto-format/auto-quality & smart cropping |
| `DELETE` | `/api/storage/*` | Securely delete an asset by public ID |

## AI Water Tank & Pump Operations (Zero Pump Sensors — 100% Ultrasonic Virtual Sensing)

In standard real-world Indian client deployments (domestic sumps, overhead tanks, campuses, hospitals), **there is NO physical sensor on the pump motor** (no electrical current CT clamps, no flow meters on the pump delivery pipe). The **only sensor installed is a top-mounted ultrasonic level sensor** measuring distance to the water surface.

This simulator implements **AI Virtual Pump Sensing & Tank Fill-Curve Profiling**:

### 1. Is this a Hypothesis or Proven Reality?
**It is 100% proven and used in production industrial IoT.**
By taking the derivative of ultrasonic water level over time ($\frac{dL}{dt}$ or $\frac{dh}{dt}$):
- $\frac{dL}{dt} \ge +0.25\%/\text{min} \implies$ **Pump is actively ON & filling the tank.**
- $\frac{dL}{dt} \le -0.15\%/\text{min} \implies$ **Pump is OFF (water is draining / normal draw).**
- $-0.15 < \frac{dL}{dt} < +0.25 \implies$ **Pump is OFF (tank is idle / static).**

### 2. Inferring Pump Mechanical Power, Pressure & Flow Rate
The slope of the refill curve ($\frac{dL}{dt}$) directly quantifies **effective pumping power**:
- For each tank, the AI trains a baseline refill model:
  $$\text{Baseline Fill Rate } (\%/\text{min}) = \frac{\text{Nominal Pump LPM}}{\text{Tank Capacity Litres}} \times 100\%$$
- **Pump Power / Pressure Efficiency Index**:
  $$\text{Pump Power Index} = \frac{\text{Observed } \frac{dL}{dt}}{\text{Baseline } \frac{dL}{dt}} \times 100\%$$
- If the index drops below 55%, the AI flags a **Pump Pressure Degradation Alert** (indicating low line voltage, worn impellers, or borewell yield depletion).

### 3. Predictive Time-to-Fill & Time-to-Overflow (TTO)
Calculated **100% from ultrasonic rate of climb without any pump sensor**:
- **Time to reach 80% auto-cutoff target**:
  $$\text{Time to 80\% (mins)} = \frac{80 - L_{\text{current}}}{\frac{dL}{dt}}$$
- **Time to reach 100% (Overflow / Spill)**:
  $$\text{TTO (mins)} = \frac{100 - L_{\text{current}}}{\frac{dL}{dt}}$$
- Forecasts the exact clock timestamp: e.g. `11:42 PM IST`. Emits predictive warning alerts (`⏱️ IMMINENT OVERFLOW`) 10 minutes *before* spillage occurs.

### 4. AI Temporal Memory & Sudden 2-Hour Drain Anomaly (Pure Ultrasonic)
- Static threshold systems fail when a tank is at 15%—it looks "normal low".
- The AI maintains temporal memory buffers from ultrasonic readings ($t - 2\text{h}$):
  $$\Delta_{\text{2h}} = \text{Level}(t - 2\text{h}) - \text{Level}_{\text{now}}$$
- If a tank drops by $> 35\%$ in 2 hours without corresponding demand, it immediately triggers a **P1 Catastrophic Leak Alert** indicating underground pipeline rupture or open drain valve.

## Enterprise Operator Identity & Domain Isolation (TOAM)

To reflect real-world enterprise operations without confusing generic terminology, this system implements **Tenant Operations Access Management (TOAM)** centered around **Operator Identities & Domain Specialists**.

### Core Architecture Principles

1. **Alternative Terminology (Strictly Non-IAM Namology)**:
   - Operators are designated by their **Operational Scope & Domain Specialization**:
     - 👑 **Root Administrator / Estate Director**: Unrestricted global oversight across all organizations and infrastructure domains (`*`).
     - ⚡ **Power Domain Specialist**: Restricted strictly to electrical infrastructure (transformers, distribution meters, feeder lines, APFC capacitor banks).
     - 💧 **Water Infrastructure Specialist**: Restricted strictly to hydraulic assets (overhead tanks, sumps, pumps, flow lines, valves).
     - ♻️ **Solid Waste Operations Specialist**: Restricted strictly to waste management assets (smart bins, hydraulic compactors, bio-methanation digesters).
     - 👁️ **Domain Auditor / Inspector (View-Only)**: Telemetry observer with audit privileges, blocked from all operational actuations.
     - 🏢 **Multi-Domain Facility Lead**: Scoped across designated systems (e.g. power + water) within assigned facilities.

2. **Granular Operational Permissions (`permissions`)**:
   - `canOperate`: When `false` (Auditor / Viewer), mutating actions (`POST /api/faults`, `DELETE /api/devices`, `POST /api/devices/:id/pump`, `POST /api/devices/:id/compact`, `POST /api/alerts/:id/acknowledge`) return **403 Forbidden**.
   - `canManageFaults`: Permission to inject and clear test faults.
   - `canViewAudit`: Access to telemetry logs and historical audit records.

3. **Organizational Scoping (`allowedOrgs`)**:
   - Restricts operators strictly to designated facilities (`college_campus`, `hospital`, `industrial_powerhouse`, etc.) or all facilities (`*`).

### Operator Authentication & Context Headers

Requests can specify the operator identity using either:
- HTTP Header: `x-operator-key: op-key-<operatorId>`
- HTTP Header: `x-operator-id: <operatorId>`
- Organization Header: `x-org-id: <orgId>`

### Operator Access Management Endpoints

| Method | Endpoint | Description | Access |
|---|---|---|---|
| `GET` | `/api/access/me` | Resolve identity, role, domains, permissions, and active org of caller | Any authenticated operator |
| `GET` | `/api/access/operators` | List all provisioned operator identities | Any authenticated operator |
| `POST` | `/api/access/operators` | Provision new operator identity with domains and permissions | **Admin / Root only** |
| `PATCH` | `/api/access/operators/:id` | Update operator domains, role, or permissions | **Admin / Root only** |
| `DELETE` | `/api/access/operators/:id` | Decommission operator identity | **Admin / Root only** |
| `POST` | `/api/access/switch` | Switch active operator identity session | Any authenticated operator |

   - When a **Power Specialist** asks about water tanks or waste bins:
     > *"Domain Access Restriction: Your identity (Power Domain Specialist) is scoped strictly to the POWER domain. Inquiries regarding water resources or waste management are restricted to their respective domain specialists."*
   - When a **Water Specialist** queries power meters:
     > *"Domain Access Restriction: Your identity (Water Infrastructure Specialist) is scoped strictly to the WATER domain."*
   - **Root Administrator** retains seamless multi-domain synthesis, receiving holistic energy, hydraulic, and waste briefings.
